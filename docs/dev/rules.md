# 개발 규칙

이 프로젝트에서 반드시 지키는 규칙이다.
각 규칙은 **[필수]** 또는 **[선택]** 으로 표시하고, 바로 아래에 이유를 한 줄로 적는다.

- 대상: 1인 개발자(나)와 내가 쓰는 AI 코딩 에이전트
- 타깃: HPC(차량용 고성능 컴퓨터, Linux + RAUC), ECU/MCU 제어기(RTOS/베어메탈)
- 관련 문서: [AGENTS.md](../../AGENTS.md), [CLAUDE.md](../../CLAUDE.md), [docs/contributing.rst](../contributing.rst), [역할별 지침](README.md#역할별-지침)

## 1. 적용 범위와 우선순위

1. **[필수]** 충돌하면 다음 순서를 따른다: upstream RAUC 규칙(`docs/contributing.rst`) → `AGENTS.md` → 이 문서 → 역할별 지침.
   - 이유: upstream에 다시 기여할 수 있게 fork의 코드는 upstream 규칙을 지켜야 한다.
2. **[필수]** RAUC 코드(`src/`, `include/`, `test/`)를 바꿀 때와, 이 프로젝트에만 쓰는 코드(앱, MCU 펌웨어, 백엔드)를 만들 때를 구분한다. 이 프로젝트 코드는 별도 디렉터리나 별도 저장소에 둔다.
   - 이유: upstream 변경을 받아 올 때 충돌을 줄인다.
   - 위치: `TODO(확인 필요)` (예: `project/` 디렉터리 또는 별도 저장소)

## 2. 저장소·브랜치·태그

| 항목 | 규칙 | 등급 |
| --- | --- | --- |
| `master` | upstream `rauc/rauc`와 동기화하는 용도로만 쓴다. 직접 커밋하지 않는다. | 필수 |
| 작업 브랜치 | `feat/<요약>`, `fix/<요약>`, `docs/<요약>`, `exp/<요약>`(실험) | 필수 |
| 통합 브랜치 | `main-project`: 이 프로젝트의 배포 기준 브랜치 | 필수 |
| 병합 | 셀프 리뷰(9장)를 통과한 뒤 `main-project`에 병합한다. | 필수 |
| 태그 | `v<MAJOR>.<MINOR>.<PATCH>`, 배포한 커밋에만 붙인다. | 필수 |
| upstream 동기화 | 월 1회 `master`를 동기화하고 `main-project`에 rebase나 merge를 한다. | 선택 |

- 이유: 혼자 일해도 "배포한 것"과 "작업 중인 것"을 브랜치로 나눠야 롤백 기준이 생긴다.

## 3. 버전 규칙

1. **[필수]** 소프트웨어 버전은 SemVer `MAJOR.MINOR.PATCH`를 쓴다.
   - MAJOR: 슬롯 구성·번들 형식·통신 인터페이스가 호환되지 않게 바뀜
   - MINOR: 기능 추가(호환 유지)
   - PATCH: 버그·보안 수정
   - 이유: OTA 다운그레이드 정책과 호환성 판단의 기준이 된다.
2. **[필수]** RAUC 번들 manifest의 값은 다음 형식을 따른다.

   | 필드 | 형식 | 예시 |
   | --- | --- | --- |
   | `compatible` | `<제품>-<장치종류>-<HW리비전>` | `mobi-hpc-r2` |
   | `version` | SemVer | `1.4.0` |
   | `build` | `<YYYYMMDD>-<git 짧은 해시>` | `20261020-041fced` |

   - 이유: `compatible`이 틀리면 다른 장치용 번들이 설치될 수 있다. R156의 소프트웨어 식별 정보로도 쓴다.
3. **[필수]** MCU 펌웨어 버전은 HPC 번들 버전과 따로 관리한다. 번들 안의 MCU 이미지 목록과 버전은 [릴리스·OTA 기록](templates/release-ota.md)에 남긴다.
   - 이유: 하나의 번들이 여러 MCU를 업데이트하므로 개별 추적이 필요하다.

## 4. 커밋 규칙

1. **[필수]** 커밋 하나에는 개념 하나만 담는다. 제목은 `<경로 또는 영역>: <명령형 요약>` 형식으로 쓴다.
   - 예: `src/nbd: keep credentials when effective URL drops userinfo`
   - 이유: upstream 형식과 같아야 그대로 기여할 수 있다.
2. **[필수]** 모든 커밋에 실명으로 `Signed-off-by:`를 붙인다 (`git commit -s`).
   - 이유: upstream이 DCO 1.1을 요구한다.
3. **[필수]** AI를 저자나 공동 저자로 적지 않는다. 표기하고 싶으면 `Assisted-by:`만 쓴다. 자세한 내용은 [AGENTS.md](../../AGENTS.md#commits-and-pull-requests)를 따른다.
   - 이유: upstream 정책이고, 코드의 책임은 사람에게 있다.
4. **[필수]** 커밋 본문이나 PR에 관련 요구사항 ID(`REQ-…`)를 적는다.
   - 이유: 요구사항 → 코드 → 테스트로 이어지는 추적성을 지킨다.

## 5. 코드 품질 기준

| 언어/대상 | 포매터 | 린터·정적분석 | 통과 조건 | 등급 |
| --- | --- | --- | --- | --- |
| C (RAUC) | `./uncrustify.sh` | `-Dwerror=true`, scan-build | 경고 0, 포맷 변경 없음 | 필수 |
| C (MCU) | clang-format | MISRA C:2012 검사기, cppcheck | 필수 규칙 위반 0, 예외는 기록 | 필수 |
| C++ (HPC 앱, ROS 2) | clang-format | clang-tidy, `-Wall -Wextra -Werror` | 경고 0 | 필수 |
| Python | `ruff format` | `ruff check`, 타입 힌트 | 오류 0 | 필수 |
| Rust | `cargo fmt` | `cargo clippy -D warnings` | 경고 0 | 선택 |
| 셸 스크립트 | — | shellcheck | 오류 0 | 필수 |

- MISRA 검사기: `TODO(확인 필요)` (상용 도구 또는 cppcheck MISRA 애드온)
- MISRA 예외는 [ADR](templates/adr.md)에 근거와 함께 남긴다.
- 이유: 혼자서는 리뷰어가 없으므로, 기계가 잡을 수 있는 문제는 모두 도구로 막는다.

## 6. 테스트 기준

| 수준 | 대상 | 도구 | 언제 | 등급 |
| --- | --- | --- | --- | --- |
| 단위 | 함수·모듈 | GLib test, pytest, Unity/Ceedling(MCU), gtest | 매 커밋 | 필수 |
| 통합(가상) | HPC OTA 흐름 | `./qemu-test` | 병합 전 | 필수 |
| SIL | MCU 로직, 제어 알고리즘 | 호스트 빌드 + 시뮬레이터 | 병합 전 | 필수 |
| HIL | 실제 HPC + MCU + CAN | 벤치 | 릴리스 전 | 필수 |
| 전원 차단 | OTA 중 전원 차단 | 벤치 + 전원 릴레이 | 릴리스 전 | 필수 |
| 시뮬레이션 | 로봇·주행 시나리오 | Gazebo 등 `TODO(확인 필요)` | 기능 변경 시 | 선택 |

1. **[필수]** 버그를 고치면 그 버그를 재현하는 테스트를 먼저 추가한다.
   - 이유: 같은 버그가 다시 생기는 것을 막는다.
2. **[필수]** 실패한 테스트를 건너뛰거나 지울 때는 이유와 다시 살릴 조건을 [이슈 보고서](templates/incident.md)에 남긴다.
   - 이유: 조용히 사라진 테스트는 안전 근거를 잃게 만든다.
3. **[필수]** 호스트에서 `sudo`로 테스트하지 않는다. 테스트는 QEMU나 벤치에서 돌린다.
   - 이유: 개발 PC의 디스크를 망가뜨릴 수 있다.

## 7. 안전 규칙

1. **[필수]** 부팅 중인 슬롯(HPC)과 실행 중인 뱅크(MCU)에는 절대 쓰지 않는다.
   - 이유: 업데이트가 실패해도 돌아갈 곳이 있어야 한다.
2. **[필수]** 업데이트 중 어느 시점에 전원이 끊겨도 장치는 부팅할 수 있어야 한다. 순서는 다음과 같다.
   1. 대상 슬롯을 bad로 표시
   2. 쓰기
   3. `fsync`·검증
   4. 부팅 순서 변경
   - 이유: 차량은 시동 꺼짐, 크랭킹 저전압, 배터리 분리가 일상이다.
3. **[필수]** 새 버전은 부팅 후 헬스체크를 통과해야 `mark-good` 처리한다. 실패하면 자동으로 롤백된다.
   - 헬스체크 항목: 핵심 서비스 기동, MCU 통신, 진단 응답 `TODO(확인 필요)`
   - 이유: "부팅은 되지만 기능이 죽은" 상태를 정상으로 판단하지 않기 위해서다.
4. **[필수]** MCU 업데이트는 차량이 안전한 상태일 때만 허용한다. 조건은 정차, 기어 P, 전압 범위 등이며 `TODO(확인 필요)`.
   - 이유: 주행 중 제어기 재부팅은 위험하다.
5. **[필수]** 안전 기능과 관련된 변경은 [간이 HARA](templates/hara.md)를 갱신한 뒤 진행한다.
   - 이유: 영향 분석 없이 안전 관련 코드를 바꾸지 않는다.
6. **[필수]** 이 프로젝트의 산출물은 ISO 26262 인증을 받은 것이 아니다. 문서와 코드에 "준수", "인증" 표현을 쓰지 않고 "참고" 또는 "준용"으로 쓴다.
   - 이유: 근거 없는 안전 주장은 법적·기술적 위험이 된다.

## 8. 보안 규칙

1. **[필수]** 개인키, 토큰, 비밀번호는 저장소에 커밋하지 않는다. 개발 키와 운영 키를 분리하고, 운영 키는 HSM이나 오프라인 저장소에 둔다.
   - 키 보관 방법: `TODO(확인 필요)`
   - 이유: 서명 키가 유출되면 모든 차량에 악성 업데이트를 배포할 수 있다.
2. **[필수]** 모든 번들은 서명하고, 장치는 서명이 검증된 번들만 설치한다. 번들 형식은 `verity` 이상을 쓰고, 기밀이 필요하면 `crypt`를 쓴다.
   - 이유: R155/R156과 ISO/SAE 21434의 무결성 요구를 충족하는 기본 조건이다.
3. **[필수]** 서명 검증을 끄는 옵션이나 디버그 우회 코드는 운영 빌드에 넣지 않는다.
   - 이유: 개발용 우회가 출시 제품에 남는 사고가 흔하다.
4. **[필수]** 릴리스마다 SBOM(SPDX 또는 CycloneDX)을 만들고 보관한다.
   - 이유: 취약점이 공개됐을 때 영향받는 차량을 찾을 수 있어야 한다.
5. **[필수]** 취약점은 다음 기한 안에 대응한다.

   | 심각도(CVSS) | 분석 | 수정 배포 |
   | --- | --- | --- |
   | Critical (9.0 이상) | 2일 | 14일 |
   | High (7.0–8.9) | 7일 | 30일 |
   | Medium 이하 | 30일 | 다음 정기 릴리스 |

   - 이유: 기한이 없으면 1인 개발에서는 보안 대응이 계속 밀린다.
6. **[필수]** 위치, 운행 기록, 영상 같은 개인정보는 수집 목적을 [인터페이스 정의서](templates/interface.md)에 적고, 최소한으로만 수집한다.
   - 이유: 개인정보보호법, 위치정보법, GDPR.

## 9. 셀프 리뷰 절차

사람 리뷰어가 없으므로 아래 절차로 대신한다.

1. **[필수]** 작성한 코드는 바로 병합하지 않는다. 최소 하룻밤(약 12시간) 뒤에 diff를 다시 읽는다.
   - 이유: 시간을 두면 작성자의 맹점이 줄어든다.
2. **[필수]** 병합 전에 아래 체크리스트를 PR 본문에 붙이고 모두 확인한다.

   ```markdown
   - [ ] 관련 REQ ID를 적었다
   - [ ] 포매터·린터·정적분석을 통과했다
   - [ ] 새 동작·버그 수정에 테스트를 추가했다
   - [ ] QEMU(또는 SIL) 테스트를 통과했다
   - [ ] 부팅 중인 슬롯·실행 중인 뱅크에 쓰지 않는다
   - [ ] 전원 차단 시 동작을 생각했다
   - [ ] 외부 입력(번들, 네트워크, CAN, D-Bus)을 검증한다
   - [ ] 비밀 정보가 diff에 없다
   - [ ] 문서·CHANGES·양식을 갱신했다
   ```

3. **[선택]** AI 코드 리뷰(`/code-review`)를 보조로 쓴다. 지적 사항은 직접 판단해 반영하고, AI가 "문제없음"이라고 한 것을 근거로 삼지 않는다.
   - 이유: AI 리뷰는 놓치는 것이 있고, 최종 책임은 나에게 있다.
4. **[필수]** 서명·암호화·부트 선택·MCU 플래싱 로직을 바꿀 때는 [ADR](templates/adr.md)을 먼저 쓴다.
   - 이유: 가장 위험한 변경은 결정 근거를 남겨야 나중에 검증할 수 있다.

## 10. 완료 정의 (DoD)

작업 하나가 "완료"이려면 다음을 모두 만족해야 한다.

- [ ] 요구사항 ID와 연결됨
- [ ] 코드 품질 기준(5장) 통과
- [ ] 테스트 기준(6장)의 해당 수준 통과
- [ ] 셀프 리뷰(9장) 체크리스트 완료
- [ ] 관련 문서·양식 갱신
- [ ] 릴리스에 포함되면 [릴리스·OTA 기록](templates/release-ota.md) 작성
