# 오토모티브 개발 지침

공통 규칙은 [rules.md](../rules.md)를 따른다. 이 문서는 차량 통신, 진단, 기능안전, 사이버보안 관점에서 추가로 지킬 내용이다.

## 1. 목적

HPC와 ECU/MCU가 차량 네트워크에서 안전하고 안정적으로 통신하게 한다. 차량 규제(R155, R156)에 대응할 수 있는 근거를 남긴다.

## 2. 적용 범위

| 대상 | 내용 |
| --- | --- |
| 차량 네트워크 | CAN, CAN-FD, 차량 Ethernet(SOME/IP, DoIP) |
| 진단 | UDS(ISO 14229), DTC, 플래싱 시퀀스 |
| 전원·상태 관리 | 점화(KL15/KL30), 슬립·웨이크업, 저전압 |
| 안전·보안 분석 | 간이 HARA, 간이 TARA |
| 제외 | 클라우드 백엔드(→ [mobility-maas.md](mobility-maas.md)) |

## 3. 설계 원칙

- **통신 정의는 기계가 읽는 파일이 원본이다.** CAN은 DBC, SOME/IP는 ARXML 또는 FIDL로 정의하고, 코드는 가능하면 생성한다.
- **안전 관련 신호는 E2E 보호를 한다.** CRC, alive counter, 타임아웃을 쓰고, 수신 측의 타임아웃 시 동작(안전 상태)을 정의한다.
- **진단 접근은 보안 접근(0x27) 또는 인증(0x29)으로 보호한다.** 플래싱과 쓰기 서비스는 Programming 세션에서만 허용한다.
- **전원 모드를 고려한다.** 모든 기능은 KL15 off, 저전압, 크랭킹 중 동작을 정의한다. OTA와 MCU 플래싱은 안전 상태 조건(REQ-SAF-…)을 만족할 때만 진행한다.
- **안전·보안 등급이 다른 기능을 분리한다.** HPC(Linux, QM)는 안전 기능을 직접 수행하지 않고, 안전 기능은 MCU에서 독립적으로 동작한다.

## 4. 구현 체크리스트

- [ ] 새 메시지·신호를 DBC/ARXML과 [인터페이스 정의서](../templates/interface.md)에 반영했다
- [ ] 안전 관련 신호에 E2E 보호와 타임아웃 처리가 있다
- [ ] 송신 주기와 버스 부하를 계산했다 (CAN 부하 목표 `TODO`% 이하)
- [ ] UDS 서비스별 세션·보안 접근 조건을 정의했다
- [ ] DTC 목록과 발생·해제 조건을 정의했다
- [ ] 플래싱 시퀀스에 중단 후 재개 절차가 있다
- [ ] 저전압·KL15 off 시 동작을 정의했다
- [ ] 변경이 안전 기능에 닿으면 [HARA](../templates/hara.md)를, 외부 통신에 닿으면 [TARA](../templates/tara.md)를 갱신했다

## 6. 관련 표준 (참고·준용 수준)

| 표준 | 적용 부분 |
| --- | --- |
| ISO 26262 | 간이 HARA, 안전 목표, 안전 요구사항 도출 |
| ISO/SAE 21434 | 간이 TARA, 보안 요구사항, 취약점 관리 |
| UNECE R155 | 사이버보안 관리 근거 (TARA, 모니터링) |
| UNECE R156 | 소프트웨어 업데이트 관리 근거 ([release-ota](../templates/release-ota.md)) |
| ISO 14229 (UDS) | 진단·플래싱 서비스 |
| AUTOSAR E2E, SecOC | 신호 보호 방식 참고 |

인증을 받은 것이 아니므로 "준수", "인증" 대신 "참고", "준용"으로 쓴다.

## 7. 흔한 실수

- DBC와 코드의 신호 정의가 어긋난다 (코드 생성을 하지 않아서).
- 수신 타임아웃 시 마지막 값을 계속 쓰고, 안전 상태로 가지 않는다.
- 진단 보안 접근을 개발 편의로 꺼 둔 채 출시한다.
- 플래싱 중 다른 ECU의 주기 메시지 때문에 버스 부하가 커져 플래싱이 실패한다.
- HARA 없이 "QM이니까 괜찮다"고 가정한다.
