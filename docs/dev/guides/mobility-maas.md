# MaaS·모빌리티 서비스 개발 지침

공통 규칙은 [rules.md](../rules.md)를 따른다. 이 문서는 차량·로봇과 연결되는 클라우드 서비스(OTA 서버, 장치 관리, 배차, 운행 데이터)를 만들 때 추가로 지킬 내용이다.

## 1. 목적

차량과 로봇을 원격으로 안전하게 관리하고, 서비스 기능(배차, 경로, 운행 기록)을 제공한다. 차량 측 장애가 서비스 전체로 번지지 않게 한다.

## 2. 적용 범위

| 대상 | 내용 |
| --- | --- |
| OTA 백엔드 | 번들 저장·배포, 단계적 배포, 설치 결과 수집 |
| 장치 관리 | 장치 등록·인증서 발급, 상태·DTC 수집 |
| 서비스 | 배차, 경로, 예약, 운행 기록 `TODO(확인 필요)` |
| 인프라 | `TODO(확인 필요)`: 클라우드 사업자, 직접 운영 서버 |
| 제외 | 차량 내부 통신(→ [automotive.md](automotive.md)) |

## 3. 설계 원칙

- **장치 인증은 장치별 인증서로 한다 (mTLS).** 공유 비밀번호나 URL에 넣는 계정 정보는 쓰지 않는다. RAUC 스트리밍에서도 URL 인증 정보 대신 클라이언트 인증서나 헤더를 쓴다. libcurl 8.18 환경에서 URL 인증 정보가 첫 요청 뒤 사라지는 결함이 확인됐다 (`src/nbd.c` 리다이렉트 처리).
- **OTA는 단계적으로 배포한다.** 벤치 → 시험 장치 1대 → 일부 → 전체 순서로 배포하고, 실패율이 기준을 넘으면 자동으로 멈춘다.
- **원격 명령은 최소화한다.** 차량 동작에 영향을 주는 원격 명령은 차량 측에서 다시 안전 조건을 확인한다. 서버는 "요청"만 하고, 실행 여부는 차량이 결정한다.
- **오프라인을 기본으로 가정한다.** 차량은 언제든 연결이 끊긴다. 모든 API는 재시도에 안전해야 한다(멱등성).
- **개인정보는 최소 수집, 짧은 보관이 원칙이다.** 위치·운행 데이터는 목적별로 보관 기간을 정하고 자동 삭제한다.

## 4. 구현 체크리스트

- [ ] API를 OpenAPI 또는 `.proto`로 정의하고 [인터페이스 정의서](../templates/interface.md)에 연결했다
- [ ] 모든 쓰기 API에 멱등 키 또는 버전 검사가 있다
- [ ] 장치 인증서의 발급·폐기(CRL/OCSP) 절차가 있다
- [ ] OTA 배포에 대상 필터(`compatible`, HW 리비전, 현재 버전)가 있다
- [ ] 단계적 배포의 중단 기준(실패율 `TODO`%)이 있다
- [ ] 설치 결과·롤백 이벤트를 [릴리스·OTA 기록](../templates/release-ota.md)으로 남길 수 있다
- [ ] 개인정보 항목별 목적·보관 기간·삭제 방법을 정의했다
- [ ] 비밀 정보는 시크릿 관리 도구에 두고 코드·설정 파일에 없다

## 5. 테스트·검증

| 항목 | 방법 | 수준 |
| --- | --- | --- |
| API 로직 | 단위 테스트, 계약 테스트(OpenAPI 스키마 검증) | 단위 |
| 장치 연동 | `./qemu-test system`의 RAUC를 OTA 서버에 연결 | 통합(가상) |
| 단계적 배포·중단 | 가짜 장치 다수로 실패 주입 | 통합 |
| 오프라인·재연결 | 네트워크 단절·지연 주입 | 통합 |
| 보안 | 인증 우회, 권한 상승, 입력 검증 점검 (OWASP API Top 10) | 릴리스 전 |
| 부하 | 동시 장치 수 `TODO`대 기준 | 선택 |

참고: 저장소의 `contrib/polling-server`는 RAUC 폴링 테스트용 예시 서버다.

| GTFS, GBFS | 대중교통·공유 모빌리티 데이터 연동 시 |

## 7. 흔한 실수

- 모든 장치가 같은 API 키를 쓴다. 하나가 유출되면 전부 위험해진다.
- 전체 장치에 한 번에 배포했다가 같은 결함으로 동시에 롤백된다.
- 장치가 오프라인일 때 쌓인 요청이 재연결 시 한꺼번에 몰린다.
- 위치 데이터를 "나중에 쓸지 몰라서" 무기한 보관한다.
- 서버 시간과 장치 시간의 차이를 고려하지 않아 인증서 검증이 실패한다.
